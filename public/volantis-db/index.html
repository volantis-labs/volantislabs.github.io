Embedded search database

Search that runs inside your app.

Volantis DB is one library for vector, full-text and hybrid search, with a graph you query in Cypher. Give it text, get text back: our on-device model pair does the embedding. No server, no API keys, no network hop.

Text in, text out

Two towers. One shared space.

You give Volantis DB text and get text back. Inside, a specialized asymmetric model pair runs on your Mac. A document tower reads each passage once, when you write it. Our own small query tower reads each question, every time you search. We trained it to land in the same 384-dimension space as the documents. So a short question finds the right passage, even in another language.

No hop

The engine runs in your process. A query is a function call, with no socket, no serialization and no second process.

Small codes, exact answers

A Vamana graph walks 4-bit RaBitQ codes to find candidates, then scores the best ones again with full float32 vectors.

Kernels for your CPU

NEON or AVX2 kernels, chosen at run time. On an M3 Max, one 768-dimension int8 distance takes 10 ns. Segments are memory-mapped and immutable.

One store

Four ways to search. One store.

Vector, full-text, hybrid and graph queries read the same documents, with one ID space and one snapshot. You do not keep two systems in step.

Vector

Nearest neighbours for embeddings from any model. Approximate graph search by default. Exact search when you must see every match.

float32 · k-NN

Full text

BM25 with stemming, accent folding and prefix search for type-ahead. It finds exact words, codes and names that embeddings can miss.

BM25

Hybrid

Runs vector and full-text search on the same snapshot, then fuses the two rankings. Good when a query has both meaning and key words.

vector + BM25, fused

Graph

A property graph in the same store. Query it with openCypher, and call vector or hybrid search inside the query.

        Quick start

        Text in. Text out.

        1. Install one package.The native engine comes with it. There is nothing else to run.
        2. Open a folder.The folder is the database. Reopen it later and your committed data is there.
        3. Add text.The document tower embeds it once, as you write. Long text is split into chunks for you.
        4. Ask in words.The query tower embeds the question. You get the matching text back, ranked. Choose vector, full text or hybrid.

        Have your own embeddings? Every API also takes float32 vectors. See the docs.

    )?;

                                QueryOptions::new(5).with_legs(Legs::Hybrid))?;

    }
    store.close()?;
    Ok(())
}

#include <stdio.h>
#include <string.h>

int main(void) {
    ZeTextModelRef model = { .abi_size = sizeof(model) };
    ze_text_default_model(&model);              /* pinned model pair, borrowed */
    ZeTextOpenModelRequest open = { .abi_size = sizeof(open) };
    open.store.abi_size = sizeof(open.store);
    open.store.path = (const uint8_t *)"text-store"; open.store.path_len = 10;
    open.store.commit_tier = 1;                 /* ordered */
    open.store.reader_drain_timeout_ms = 250;
    open.store.max_resident_bytes = UINT64_MAX; open.store.max_temp_bytes = UINT64_MAX;
    open.repo = model.repo; open.repo_len = model.repo_len;
    open.revision = model.revision; open.revision_len = model.revision_len;
    open.manifest_sha256 = model.manifest_sha256;
    open.manifest_sha256_len = model.manifest_sha256_len;
    ze_handle store = 0;
    if (ze_text_open_model(&open, &store) != ZE_OK) return 1;

    const char *text = "The bronze airship flies above the city.";
    ZeTextDocument doc = { .abi_size = sizeof(doc), .doc_id = { .low = 1 }, .revision = 1,
                           .text = (const uint8_t *)text, .text_len = strlen(text) };
    ZeTextIngestRequest ingest = { .abi_size = sizeof(ingest), .documents = &doc,
        .document_count = 1, .embed_batch_size = 1, .seal_every = 1, .channel_capacity = 1 };
    ZeMutationReport report = { .abi_size = sizeof(report) };
    if (ze_text_ingest(store, &ingest, &report) != ZE_OK) return 1;

    const char *q = "airship over the city";
    ZeTextQueryRequest query = { .abi_size = sizeof(query), .text = (const uint8_t *)q,
                                 .text_len = strlen(q), .k = 5, .legs = 2 /* hybrid */ };
    ZeTextQueryResult result = { .abi_size = sizeof(result) };
    if (ze_text_query(store, &query, &result) != ZE_OK) return 1;
    printf("%zu hits\n", result.hit_count);
    ze_text_query_result_free(&result);
    return ze_close(store) == ZE_OK ? 0 : 1;
}
        Production controls

        Built like a database, not a demo.

        Search is only half the job. The other half is what happens when the app crashes, the disk fills or a query takes too long.

        Crash safe

        Writes go through a write-ahead log. If the app is killed, every acknowledged write is there when you reopen. For power loss, turn on the durable mode, which syncs to disk.

        One snapshot per query

        Each commit publishes an immutable generation. A query reads one generation and tells you which one.

        Typed filters

        Filter on typed attributes and time ranges. Filters apply to each search leg before ranking, not after.

        Safe retries

        Every document has a revision. Send the same write again and nothing changes. An older revision is refused, so a slow retry cannot undo a new edit.

        Deadlines and cancel

        Give a query or a write a deadline, or cancel it. In Node, pass an AbortSignal.

        Memory budgets

        Set how much resident memory and temporary disk a store may use. The engine refuses work before it goes over.

        Retention and purge

        Keep old generations as long as you need them. Purge removes deleted data from the disk, not only from results.

        Query diagnostics

        Each result says which path ran (approximate or exact), the bytes it read and the documents it scored.

        Embed later

        Commit text now and let a background worker embed it. Full-text search finds the new row at once.

        Honest limits

        When not to use it.

        Volantis DB is new. Here is what it does not do yet, so you can decide fast.

        You need a server.

        Volantis DB is a library inside one app, with one writer for each store. It has no network protocol and no replication. If many machines must share one database, use a server database.

        You ship on Linux, iOS or Android.

        Today it runs on macOS (Apple silicon and Intel) and Windows x64. Other platforms are not supported yet.

        You need the text model on Windows.

        Windows has the full engine, but no on-device model yet. Bring your own vectors there.

        You need graph search from Python.

        The Python wheel has no graph support yet, and it is for Apple silicon only. Use Node.js, Swift, Rust or C for the graph.

        You need all of Cypher.

        The graph speaks a bounded openCypher profile. It has no MERGE, UNWIND, UNION or shortest path, and traversals stop at 16 hops.

        Your app cannot use GPL code.

        Volantis DB is GPL-3.0. If you ship it inside your app, the GPL applies to how you ship that app. Read the license before you build on it.

        Free. Open source. In your process.

        Volantis DB is free software under GPL-3.0. Read every line that touches your data. The only network call is the optional model download, and you can turn it off.
