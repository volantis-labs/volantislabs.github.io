Summary

  • On three BEIR datasets, Volantis DB had the lowest p95 vector-search latency of six in-process libraries: 0.06 ms on SciFact, 0.11 ms on TREC-COVID and 0.88 ms on Natural Questions.
  • It got there at the same nDCG@10 as the others, to two decimal places, on SciFact and Natural Questions. On TREC-COVID, Chroma is a little more accurate (0.84 against 0.83).
  • The margin is large on SciFact and TREC-COVID (9× to 56× against the next libraries) and small on Natural Questions (1.5× against Chroma).
  • Hybrid search beat vector-only and BM25-only search on SciFact in our tuning run (nDCG@10 0.764 against 0.718 and 0.692).
  • All numbers are from one machine: an Apple M3 Max MacBook Pro. We have not measured Windows yet.

Method

Datasets

BEIR is a public benchmark for information retrieval. We used three of its datasets:

  • SciFact: find scientific evidence for a claim.
  • TREC-COVID: find biomedical papers for COVID-19 research questions.
  • Natural Questions: find Wikipedia passages for real search-engine questions.

What we measured

  • p95 latency: the time under which 95% of the queries finish, in milliseconds. One query asks for the top k = 10.
  • nDCG@10: the standard BEIR quality score for the top 10 results. Higher is better, 1.0 is perfect.
  • Warm indexes: each index was built and loaded before the timed queries. Cold start is a different number (see text API latency).
  • Vector search only: each library got precomputed query vectors. Embedding time is not in these numbers.

Machine

MacBook Pro with an Apple M3 Max and 128 GB of memory, macOS 27.0. The SIMD calibration for this machine is in the repo at crates/volantis-db-bench/calibrations/apple-m3-max-mac15-9.json.

Libraries

Chroma, hnswlib, LanceDB, sqlite-vec and USearch, each running in process on the same machine. We compare at the accuracy each library reached, so a fast result with a low nDCG@10 does not count as a win.

Not published yet. The harness that ran the five other libraries, their versions and index settings, and the raw per-query results are not in the public repo today. Until they are, treat these numbers as our own claim, and check them on your data. We will gladly take fixes to how we set up any library.

Why it is fast

  • No hop. The engine runs in your process. A query is a function call: no socket, no serialization, no second process.
  • Small codes first. Each sealed segment has a Vamana graph. The walk reads 4-bit Extended-RaBitQ codes, which need no training. Then the best candidates are scored again with full float32 vectors, so the final order is exact for those candidates.
  • The right tier for the size. On SIFT-128, a graph was 4.24× faster than a full scan at 30,000 rows (k = 10, recall 0.9985), but only 1.82× faster at 10,000 rows. So a segment gets a graph at 30,000 rows, and small segments use an exact scan.
  • Kernels for your CPU. Scalar, NEON and AVX2 code paths, chosen at run time. Property tests check every SIMD path against the scalar one.
  • Memory-mapped, immutable segments. Reads need no locks and no copies. Full-text posting blocks hold 64 entries, sized to the 128-byte cache line of Apple silicon.

Hybrid quality

On BEIR SciFact, with Cohere embed-english-v3 vectors and the 300 judged queries, measured on 26 August 2026:

ModenDCG@10
Hybrid (vector + BM25)0.7642
Vector only0.7181
BM25 only0.6917

Hybrid weights from 0.6 to 0.8 stayed within one point. This run used an earlier score normalization. The current fusion policy was tuned again on SciFact, FiQA and TREC-COVID, so its numbers can be a little different. Hybrid in the Store API uses a weighted sum (default weight 0.7 on the vector side). Embedded namespaces use reciprocal rank fusion.

Full-text quality

The BM25 engine uses the standard settings (k1 = 1.2, b = 0.75). A quality gate checks that its nDCG@10 is within 2 points of Pyserini, the reference BM25 for BEIR, on four datasets. The gate passed on 23 August 2026. Its floors are:

Cost of durability

The default mode does not call fsync on each write. That keeps writes fast, and a killed process still keeps every acknowledged write. A power cut can lose the most recent writes. If the store is the only copy of the data, choose the durable mode. On our test Mac, a 4 KiB write with a full sync took 20.8× the median time of an ordered write.

Caveats

  • One machine, Apple silicon only. Your hardware and data will give different numbers.
  • The BEIR chart is the result of one setup of each library. A different index setting can move a library a lot.
  • The rival harness, versions, settings and raw results are not published yet.
  • The text API table is for the earlier default model.
  • Search-lab timings come from a tiny corpus. They show the cost of the query embedding, not the cost of search at scale.

Run it yourself

The benchmark tools are in the volantis-db repo:

  • crates/volantis-db-bench: BEIR loader and evaluation, recall harness, hybrid and planner sweeps.
  • tools/lexical-bakeoff: BM25 against tantivy and SQLite FTS5.
  • scripts/bench-text-memory.sh: memory use during text ingest.

The search-lab and graph recordings on this site come from tools/volantis-db-demo in the site repo. Each script opens the real engine, runs the queries and saves the output.

git clone https://github.com/volantis-labs/volantis-db.git
cd volantis-db
cargo test --workspace
cargo run --release -p volantis-db --example five_vectors_search
